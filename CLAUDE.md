## Architecture

RESOLVE is a **standalone C++ engine** (libtorch) with thin nanobind/Rcpp language bindings.

```
+------------------------------------------------------------------+
|                  RESOLVE C++ Engine (libtorch)                   |
|                                                                  |
|  Data Layer:                                                     |
|  - CSV loading (hand-rolled reader)                              |
|  - Role mapping (plot_id, species_id, coords, taxonomy, etc.)    |
|  - ResolveDataset.from_csv() - high-level API                    |
|                                                                  |
|  Encoding Layer:                                                 |
|  - Feature hashing (species -> hash vector)                      |
|  - Taxonomy encoding (genus/family -> embeddings)                |
|  - TaxonomyVocab                                                 |
|                                                                  |
|  Model Layer:                                                    |
|  - ResolveModel (MLP with multi-head output)                     |
|  - CUDA kernels (hash embedding, etc.)                           |
|                                                                  |
|  Training Layer:                                                 |
|  - Trainer (dataset-first API)                                   |
|  - Loss functions (PhasedLoss, MultiTaskLoss)                    |
|  - Metrics (band accuracy, MAE, RMSE, SMAPE)                     |
|                                                                  |
|  Inference Layer:                                                |
|  - Predictor with confidence thresholds                          |
|  - Embedding extraction                                          |
+------------------------------------------------------------------+
                              |
         +--------------------+--------------------+
         |                    |                    |
         v                    v                    v
+----------------+  +----------------+  +----------------+
|  R bindings    |  | Python bindings|  |     CLI        |
|   (Rcpp)       |  |  (nanobind)    |  |  (standalone)  |
+----------------+  +----------------+  +----------------+
```

## Design Goals

1. **Standalone C++ engine** - Complete functionality without any language runtime
2. **CLI tool** - Train and predict from command line
3. **Thin bindings** - R/Python wrappers around C++ are just API translations, no logic
4. **Single source of truth** - The C++ engine is the only implementation; every binding reaches the same code.

- **R package builds on Windows via a C ABI facade (issue #17)**: the R package no longer `#include`s libtorch or links it directly, so the recurring "Rcpp can't compile on this Windows host — mingw rejects the MSVC CUDA libtorch headers" wall (the issue #12 / #14 / #16 toolchain notes above) is **removed**. A flat `extern "C"` facade (`include/resolve/resolve_capi.h` + `cpp_src/resolve_capi.cpp`) wraps the engine behind opaque handles (`resolve_dataset_t` / `resolve_model_t` / `resolve_trainer_t` / `resolve_predictor_t`) and a single `resolve_value_t` tagged tree (scalars / arrays / row-major double|int matrices / ordered maps / lists) that carries all structured input (roles / targets / config / forward inputs) and output (results, accessor tensors) across the boundary. No `torch::Tensor`, `std::string`, STL, or Rcpp type crosses the C line; only `double*` / `int64_t*` / `const char*` / lengths / opaque pointers / `int` status codes do. All tensor↔buffer marshaling, the config/enum parsers (moved out of `r/src/rcpp_common.h`), and the result-struct→tree converters live on the MSVC side in `resolve_capi.cpp`; C++ exceptions are translated to a thread-local `resolve_last_error()` + a NULL/`-1` return. - **Windows process hardening: teardown crash + JIT-debugger hang (issues #18 / #19)**: a single engine module `resolve::process` (`include/resolve/process.hpp` + `cpp_src/process.cpp`, mirroring the `gpu.hpp` standalone-helper pattern) turns a native fault from a hang or a launcher-teardown crash into a fast, deterministic exit. `install_crash_handler(shutdown_exit_code)` (Windows-only; no-op elsewhere) sets `SetErrorMode(SEM_FAILCRITICALERRORS | SEM_NOGPFAULTERRORBOX | SEM_NOOPENFILEERRORBOX)`, `WerSetFlags(WER_FAULT_REPORTING_NO_UI)` (dynamically resolved from kernel32, no wer.lib link), a `SetUnhandledExceptionFilter` (mid-run faults), and a first-in-line `AddVectoredExceptionHandler` (teardown-window faults the unhandled filter never sees). Both terminate via `TerminateProcess`, which never consults the AeDebug `vsjitdebugger` key -- so a headless worker that hits an unhandled native exception fails fast with the fault's NTSTATUS instead of hanging forever on the JIT-debugger handshake (issue #19, observed as a `0xC0000006` worker holding the GPU ~13 h). `signal_work_complete()` flips the policy so a fault during normal teardown-after-success exits with the shutdown code (0) rather than a failure code; the exit-code split is the pure, unit-tested `crash_exit_code()`. `set_thread_pools(intraop, interop)` pins libtorch's host pools (the `at::set_num_threads(1)` mitigation #18 points at: no worker threads to join during process exit, the suspected teardown-race source). - **Exact 1.5-entmax + live `use_sparsemax` (2026-08-06, issue #103)**: `TabNetConfig::use_sparsemax` was documented as "Use sparsemax vs entmax-1.5", persisted through the checkpoint / C ABI / nanobind, and changed nothing — `TabNetStepImpl::attentive_forward` hardcoded `sparsemax(logits, -1)` and `entmax15` had zero call sites in the engine. `entmax15` was also not the published operator: it solved `[z - tau]_+^2` by 20-step bisection, dropping the `(alpha - 1)` factor of `alpha-entmax(z) = [(alpha - 1) z - tau 1]_+^(1/(alpha - 1))` (Peters, Niculae & Martins, "Sparse Sequence-to-Sequence Models", ACL 2019, arXiv:1905.05702, **Eq. 13**), so it ran the operator at a different temperature and collapsed onto sparsemax's support — on `z = [1, 0, 0]` it returned the one-hot `[1, 0, 0]` where 1.5-entmax is `[0.74025, 0.12987, 0.12987]`. `entmax15` (`cpp_src/attention.cpp`) is now the paper's exact sort-based **Algorithm 2** for alpha = 1.5, transcribed verbatim in a source comment and vectorized over rho and over every slice of an arbitrary `dim` (cumulative mean `M(rho)`, centered sum of squares `S(rho)`, `tau(rho) = M(rho) - sqrt((1 - S(rho))/rho)`, support size = the count of `tau(rho) <= z_[rho]`, output `[z/2 - tau]_+^2`), matching the reference implementation `deep-spin/entmax`'s `entmax15`. Bisection (the paper's Algorithm 1) is the general-alpha `entmax_bisect` routine and is deliberately NOT implemented: alpha = 1.5 is the only value the engine uses, and shipping an unreachable general path would recreate exactly the dead-knob this issue is about. The backward is a hand-written `torch::autograd::Function` implementing the closed-form **Proposition 1** Jacobian `diag(s) - s s^T / ||s||_1` with `s_i = (p*_i)^(2 - alpha) = sqrt(p*_i)` on the support, rather than autograd through the sort/sqrt (line 5's discriminant is clamped past the support, where sqrt's derivative is not finite); scores are centered on the row max (alpha-entmax is shift invariant) and the threshold search is promoted to fp32 when the caller is fp16/bf16. `TabNetStepImpl` / `TabNetEncoderImpl` (`include/resolve/attention.hpp`) gained a trailing `use_sparsemax` ctor argument (default `true`, so every existing call site is unchanged) plus a `use_sparsemax()` accessor, and `cpp_src/adapter.cpp`'s TabNet branch passes `cfg.use_sparsemax` — the single construction site that connects `ModelConfig` to the encoder, and the one place the flag was being dropped. The remaining surface already round-tripped and needed no change, verified end to end: `cpp_src/checkpoint.cpp` (`tabnet_use_sparsemax` write + back-compat `rd_bool` read), `cpp_src/resolve_capi.cpp` `parse_tabnet_config`, `python/src/bindings_types.cpp` `TabNetConfig.use_sparsemax`, and R, where `r/src/rcpp_common.h`'s generic recursive `r_list_to_value_map` carries `list(tabnet = list(use_sparsemax = FALSE))` straight through to the same C-ABI parser. Catch2 contract in the (previously empty, already-registered) `tests/test_entmax.cpp`: Algorithm 2 values pinned for `[1,0,0]` / `[5,0,0]` / `[2,1,0,-1]` with the hand arithmetic shown in comments; simplex + shift-invariance invariants; the support ordering sparsemax <= entmax15 <= softmax (1 < 2 < 4 on the worked case, row-wise on a random batch); a double-precision central-finite-difference check of the analytic gradient plus a direct Proposition-1 comparison; arbitrary `dim` and non-contiguous (transposed / strided) inputs; both TabNet settings producing different masks from identical seeded weights with entmax keeping strictly more features; both settings training; and a `save_model_config`/`load_model_config` round-trip of `use_sparsemax = false` whose rebuilt encoder matches the entmax twin and not the sparsemax one. **Not a hard cutover for existing checkpoints — no parameter or tensor-shape change, and `use_sparsemax` defaults to `true`, so every TabNet checkpoint reloads and behaves exactly as before. The one behavioural change is for a checkpoint that recorded `use_sparsemax = false`: it now genuinely runs 1.5-entmax where it previously ran sparsemax regardless, so retrain it before comparing its numbers across the fix.**
- **Seeded pretraining + one shared pretrain loop (2026-08-06, issue #107)**: `PretrainRng` (`include/resolve/pretraining.hpp` + `cpp_src/pretraining.cpp`) is the single seam every stochastic draw in the pretraining path goes through — a dedicated `at::detail::createCPUGenerator` handle, reseeded per epoch to `seed + epoch + 1`, the same contract `Trainer::train_epoch` / `Trainer::compute_diagnostics` already hold for the training shuffle. - **libstdc++ must precede libtorch in `DT_NEEDED` on Linux (2026-08-18)**: PyTorch builds libtorch with `-static-libstdc++`, and `libtorch.so` / `libtorch_cpu.so` then export the absorbed libstdc++ symbols -- 64 and 142 `std::filesystem` entries respectively, verified with `nm -D --defined-only`. The compiler driver links libstdc++ last, so libtorch preceded it in `DT_NEEDED`, and the dynamic linker -- which takes the first definition it finds, per symbol -- resolved the engine's `std::filesystem` calls into libtorch's copy rather than the one the headers were compiled against. Against a pip libtorch (2.11.0+cu128) under GCCcore 13.3 that copy sends `std::filesystem::remove_all` through a null function pointer: `SIGSEGV`, reproducible, and it aborted the Catch2 run at 248 of 377 cases. `src/core/CMakeLists.txt` now names `stdc++` in the link-OPTIONS slot (`-Wl,--no-as-needed,-lstdc++,--as-needed`, guarded `UNIX AND NOT APPLE`), which lands ahead of the objects and of `${TORCH_LIBRARIES}` so libstdc++ takes the first `DT_NEEDED` entry; `--no-as-needed` is required because nothing is undefined at that point and the linker would otherwise drop it. A plain `target_link_libraries(resolve_core PUBLIC stdc++)` does NOT work -- CMake emits it after the torch libraries and `DT_NEEDED` is unchanged (measured). This only reorders a library the driver already links unconditionally, and ELF lookup is per-symbol, so anything absent from the toolchain's libstdc++ still falls through to libtorch's copy; preferring the libstdc++ the TU was compiled against is the ordinary arrangement. **Verified on LiSC** (L40S and T4, CUDA build, no command-line linker flags): `libstdc++.so.6` is the first `DT_NEEDED` of `resolve_tests`, `bin/resolve` AND `libresolve_c.so` -- so it propagates through the PUBLIC link to the CLI and the C ABI -- and the suite goes 377/377 cases / 4569 assertions, where it previously aborted. Ruled out along the way: a libstdc++ VERSION mismatch. A node loading GCCcore 13.3's `libstdc++.so.6` (GLIBCXX_3.4.32) rather than the system GCC 11 one (3.4.29) still segfaults, with or without an explicit `LD_LIBRARY_PATH`, so the ordering is the cause and the version is not. **Not GPU-related**: it reproduces under `CUDA_VISIBLE_DEVICES=""`, and the failing test runs on `torch::kCPU`. Production impact was nil before the fix -- the engine's only `std::filesystem` call is `create_directories` (`trainer.cpp`), which does not fault -- so no checkpoint or result is affected and nothing needs retraining. `.github/workflows/tests.yml` gains a `readelf -d` step asserting the ordering on the tests binary and the CLI before `ctest` runs; the assertion was validated against an unfixed build as a negative control (libstdc++ at position 9 and 8 vs libtorch at 4 -> rejected) so it fails on the regression it exists to catch. Shipped as `a1a92b4`; the Tests run on that SHA is green end to end, with the guard reporting libstdc++ at `DT_NEEDED` position 1 against the first libtorch at 3 for both `tests/resolve_tests` and `bin/resolve`, and `ctest` passing behind it under `-Werror` (so the added `target_link_options` raises no warning on GCC).
